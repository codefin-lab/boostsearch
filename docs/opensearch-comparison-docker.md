`opensearch-comparison.md` บันทึกกับดักนี้ไว้แล้ว (วัด obsearch สองครั้งห่างกัน
ไม่กี่สิบนาทีได้ qps 562 แล้ว 409 ทั้งที่โค้ดเดียวกัน) แต่รอบนี้ยังพลาดซ้ำ

**ตัวเลขเทียบสองเครื่องยนต์ต้องสลับฝั่งเสมอ ไม่มีข้อยกเว้น**

## อ่านผลอย่างไร

**เรื่องที่ชัด** — memory ต่างกันคนละชั้น (9.5× บน index เดียว, 4.7× บน 200 index)
และ fan-out หลาย index เราเร็วกว่าชัดเจนทุกตัว

**เรื่องที่ควรระวัง** — บน index เดียวความต่างด้าน latency อยู่ราว 1.2–1.5×
ซึ่งไม่มาก และ `agg_nested` เสมอ (1.01–1.25×) การบอกว่า "เร็วกว่า OpenSearch"
โดยไม่ระบุรูปงานจึงไม่ตรง: **จุดแข็งของเราคือ memory และ fan-out
ไม่ใช่ latency บน index เดียว**

**indexing เสมอกันใน Docker แต่ไม่เสมอกันนอก Docker** — native เราทำได้
96,646 docs/s แต่ใน container เหลือ 70,034 (−27%) ส่วน OpenSearch แทบไม่ต่าง
ค่านี้เป็นของ Docker Desktop บน macOS ไม่ใช่ของเครื่องยนต์ ยังไม่ได้ยืนยันบน
Linux host

## สิ่งที่การวัดชุดนี้ยังไม่ตอบ

- ตัวเลข absolute บน Linux host จริง (penalty ~1.9× ที่เหลือกระทบทั้งสองฝั่ง)
- workload ที่ใหญ่กว่า memory (ทั้งคู่ยัง fit)
- ความถูกต้องของผลลัพธ์ไม่ได้ diff ในการวัดรอบนี้ — ใช้ชุด test ของ OpenSearch
  แยกต่างหาก (388/398)

## แก้ครั้งใหญ่ — ตัวเลข qps ทั้งหมดก่อนหน้านี้ผิด

`tools/bench.py` เป็น Python และ **ตัน GIL ของตัวเองก่อนที่เครื่องยนต์จะตัน**
วัดเซิร์ฟเวอร์ตัวเดียวกันด้วย k6 (Go) ได้คนละเรื่อง:

| | bench.py (Python) | k6 (Go) | ผิดไป |
|---|---:|---:|---:|
| `GET /` เปล่า ๆ | 15,000 /s | **151,957 /s** | 10× |
| search | 10,144 /s | **23,182 /s** | 2.3× |

ที่จับได้เพราะใส่ตัวนับ in-flight ในเซิร์ฟเวอร์แล้วเห็นว่า **มี query อยู่ในมือแค่
1–3 ตัว ทั้งที่ client เปิด 32 thread** — ถ้าเซิร์ฟเวอร์ว่างขนาดนั้นแต่ qps ไม่ขึ้น
แปลว่าคอขวดอยู่ที่ client ไม่ใช่เซิร์ฟเวอร์

### ทำไมถึงแพ้ throughput

เราแตกงานของ query เดียวไปหลาย segment ข้าม thread — ได้ latency ดีตอนว่าง
แต่กิน CPU หลาย core ต่อ query พอทุก core มีงานของตัวเองอยู่แล้วมันคือความสูญเปล่า

| vus | แตก segment (ปัจจุบัน) | thread เดียวต่อ query |
|---:|---:|---:|
| 1 | **3,718** qps / 251 µs | 2,141 / 509 µs |
| 8 | **19,741** / 379 µs | 15,830 / 575 µs |
| 64 | 23,245 / 2.71 ms | **24,812** / 2.52 ms |

ลองทำให้ **สลับอัตโนมัติ** ตาม in-flight → ได้ 21,364 ที่ vus=64 คือ
**แย่กว่าทั้งสองแบบ** เพราะตัดสินใจทีละ query ทำให้ปนกันแล้วแย่งกันเองหนักกว่าเดิม
· revert

เก็บค่า default ไว้ (แตก segment) เพราะที่ vus=8 ซึ่งใกล้การใช้งานจริงกว่า
มันนำอยู่ 25%

ถ้าจะไล่ throughput จริงต้องลดต้นทุน CPU ต่อ query ไม่ใช่สลับ executor
